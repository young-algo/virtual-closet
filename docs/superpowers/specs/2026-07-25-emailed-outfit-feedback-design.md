# Emailed Outfit Feedback

## Goal

Make it possible to rate a daily outfit recommendation from the email itself, in one tap, without opening the app. The email becomes the single feedback surface for the daily sidecar, and the in-app feedback controls are retired.

## Current Failure

The daily outfit email contains no feedback affordance of any kind. The only way to rate a recommendation is the settings drawer in the React app, and that path is broken in a way that produces no error.

`DailyOutfitSettings.tsx` renders `DailyBundlePreview` from `loadLastDailyBundle()`, which reads `daily_outfits_last_bundle_v2`. That key is written only by the manual **Generate test bundle** action. The scheduled morning send runs entirely inside Apps Script and never reaches the browser, and `doPost` exposes no action for retrieving the bundle that was actually emailed. The preview therefore shows whatever bundle was last generated by hand, indefinitely, regardless of what was sent.

Feedback captured against that stale preview carries the stale bundle's `localDate` and `candidateId`. History entries are written only for genuinely sent bundles, by `recordSentBundleV2_` via `finalizeSentBundleV2_`. `mergeSnapshotFeedbackIntoHistoryV2_` appends the signal to whatever history entry matches the date without validating the candidate, and `dailyHistoryContextV2_` then discards any signal whose `candidateId` is not among that date's sent looks. The signal is stored and never read. No error is raised at any step.

The practical consequence is that the planner has never received a Like, Not for me, or I wore this signal.

## Requirements

- Every generated recommendation in the daily email carries three one-tap feedback links: `liked`, `disliked`, `wore`.
- A tap records the signal without requiring authentication, an app install, or a local dev server.
- A recorded signal reaches `dailyHistoryContextV2_` and influences subsequent planning through `itemFeedbackSignals`, `feedback`, and cooldown exemption via `wornItemIds`.
- A mis-tap is correctable in one further tap, from the same device, without opening the app.
- Feedback that arrives before its history entry exists is not lost.
- Encore looks carry no feedback links. Saving an outfit is already the explicit taste signal, and unsaving it is the remedy for one that has worn out its welcome.
- Test deliveries render the links for layout parity but record nothing.
- The in-app daily feedback controls are removed rather than repaired, leaving exactly one capture path.
- The on-demand stylist in `AIStylist.tsx` is untouched.
- Existing quality gates, selection policy, coverage parity, Encore cadence, and ambiguous-send recovery remain intact.

## Non-Goals

- Capturing a dislike reason. The app's reason dropdown is not reproduced; three verbs are the whole vocabulary.
- Returning the genuinely sent bundle to the browser. The email is the record of what was sent.
- Rating Encore looks.
- Any change to the on-demand stylist's prompt-steering feedback, which is ephemeral session state and never reaches the daily sidecar.

## Chosen Approach

Add a `doGet` handler to the existing web app that accepts an HMAC-signed token identifying one `(localDate, candidateId, value)` triple, records it to a dedicated Drive-backed store, and renders a confirmation page offering the other two verbs as corrections.

The store is drained into daily history by a `mergeEmailFeedbackIntoHistoryV2_()` that replaces `mergeSnapshotFeedbackIntoHistoryV2_` at its three existing Scheduler callsites.

### Why a separate store rather than a direct history write

`sendDailyBundleNowV2()` sends the email before calling `finalizeSentBundleV2_`, and `finalizeSentBundleV2_` is what creates the history entry through `recordSentBundleV2_`. A tap in that window would find no entry to attach to.

Decoupling makes arrival order irrelevant. The store is a durable inbox: an entry merges into its history entry and is then removed, and an entry whose history entry does not yet exist remains for the next run. History remains the single source the planner reads, and no second source is consulted at read time.

## Feedback Store

A new Drive file `virtual-closet-daily-v2-email-feedback.json` holds an array of entries:

```
{ localDate, candidateId, value, createdAt }
```

- `value` is one of `liked`, `disliked`, `wore`, matching the vocabulary `dailyHistoryContextV2_` already accepts.
- Upsert is last-write-wins on the `(localDate, candidateId)` pair.
- `upsertEmailFeedbackV2_` takes no lock, and neither does `doGet`. The only usable lock is the script lock, which the scheduler holds for up to five minutes during generation; taking it in `doGet` would make a tap during that window render "This link isn't valid" instead of recording. Two concurrent taps can still race: both read the store before either writes, and one write is lost silently. A same-`(localDate, candidateId)` contention detector warns when a *differing* verb lands within `DAILY_V2.FEEDBACK_CONTENTION_MS` of a prior one — enough to catch a link scanner fetching all three links in sequence, not enough to catch two truly parallel requests, and not enough to catch two writes of the *same* verb landing in that window (that path is intentionally silent, since it changes nothing).
- A corrupt or non-conforming file throws, following `parseDislikedEncoreIdsV2_`. It is never silently reset.
- Entries whose `localDate` falls outside the retention window are pruned during drain.

## Token Format

```
payload = "v1|<localDate>|<candidateId>|<value>|<test?1:0>"
url     = <WEB_APP_URL>?fb=<base64url(payload)>&s=<base64url(hmacSha256(payload, FEEDBACK_SECRET))>
```

- `FEEDBACK_SECRET` is a new required Script Property, distinct from `SYNC_SECRET`. These tokens land in browser history, and rotating one secret must not force rotating the other.
- Tokens do not expire. Replay is bounded instead by the store rejecting any `localDate` older than a new `DAILY_V2.MAX_EMAIL_FEEDBACK_AGE_DAYS` constant of 30, so links never go stale during the day they are useful. The bound is a fixed constant rather than the snapshot's `maxDailyHistoryDays`, so `doGet` need not load the snapshot to validate a token.
- A valid token authorizes exactly one triple. It permits no enumeration and reaches no other action.
- Verification failure, malformed payload, unknown `value`, and out-of-window date all render one generic invalid-link page. The cases are not distinguished in output.

`doGet` handles feedback and nothing else. Generation and sending remain `doPost`-only behind `SYNC_SECRET`.

## Configuration Changes

- Add required `FEEDBACK_SECRET`.
- Add required `WEB_APP_URL`, holding the `/exec` URL already pasted into the React settings. `ScriptApp.getService().getUrl()` is not used: it is context-dependent and can return the `/dev` URL when execution is entered from a time-driven trigger, which is unrecoverable once the email has been delivered.
- Remove `APP_URL` and the `appUrl` field from `getDailyConfigV2_`. Both exist only to render the `OPEN LATEST BUNDLE` link, which is being removed.
- A missing `FEEDBACK_SECRET` or `WEB_APP_URL` throws during render, so no email is sent with dead links.

The web app already permits anonymous access, since the React app posts to it without OAuth. No access-level change is required, only a redeploy to the existing deployment id.

## Email Rendering

Each generated look's section gains a feedback row directly beneath its monospace slot list, separated by the same `1px solid #deddd8` hairline used elsewhere in the email.

- Links are 10px monospace, uppercase, `letter-spacing:2px`, `#111` on white. No filled buttons, no bordered boxes, no color.
- The three links sit in a `<table>` row at `width:33%` each, with `display:inline-block;padding:14px 0` on each anchor to yield an approximately 44px tap target. Flexbox and `gap` are unavailable in email clients.
- The plain-text part lists the same three labelled URLs per look.
- Encore renders unchanged, with no feedback row.
- The `OPEN LATEST BUNDLE` link and its surrounding `appLink` expression are removed.

## Landing Page

`doGet` returns an `HtmlService` page in the same register as the email: white field, monospace label, hairline rule, no panel.

- The signal is recorded before the page renders. The page reports what is stored, not what was requested.
- The outfit is named, so the correct look is identifiable when the email contained three. The name is resolved by locating the `candidateId` among that date's history looks via `historyLooksV2_`. During the pre-finalize window that name is not yet available, so the page falls back to the date alone rather than blocking the write. Recording the signal never depends on resolving a display name.
- The other two verbs render as freshly signed one-tap correction links. This is what makes a mis-tap or a prefetched link recoverable without the app.
- Test-mode tokens render `Test delivery — not recorded`, write nothing, and offer no corrections.
- Invalid tokens render the generic invalid-link page.

`setXFrameOptionsMode` is not set; the page opens in a browser tab, not an iframe.

## Retiring the In-App Path

Browser removals:

| File | Change |
| --- | --- |
| `DailyFeedbackControls.tsx` | delete |
| `DailyBundlePreview.tsx` | remove `feedback` and `onFeedback` props, both lookups, and both render sites |
| `DailyOutfitSettings.tsx` | remove `feedback` state, `handleFeedback`, the prop pass, and the argument from both `buildDailySnapshot` calls |
| `storage.ts` | remove `loadDailyFeedback`, `saveDailyFeedback`, and `DAILY_STORAGE_KEYS.feedback` |
| `snapshotBuilder.ts` | remove the `feedback` parameter and the `dailyFeedback` field |
| `types.ts` | remove `DailyFeedbackV2` and the `dailyFeedback` snapshot field |

Apps Script removals:

- `mergeSnapshotFeedbackIntoHistoryV2_` in `Taste.gs`, replaced by `mergeEmailFeedbackIntoHistoryV2_` at Scheduler.gs lines 39, 82, and 143.
- The `snapshot.dailyFeedback` branch in `Encore.gs`.

`SnapshotValidation.gs` never required `dailyFeedback`, and `dislikedEncoreIdsV2` is built server-side and never sent by the browser, so removing the snapshot field breaks no validation.

Consequences accepted:

- `DISLIKED_ENCORE_IDS_V2` loses its only feed, since a `disliked` signal on an Encore was the sole source. The ledger remains empty and unsaving an outfit in the app becomes the way to retire a recurring Encore.
- The orphaned `daily_outfits_feedback_v2` localStorage key is left in place. Its contents were already being discarded downstream, so there is nothing to migrate.
- The roughly 28 `appUrl: ''` stubs across the contract tests become inert extra keys and are left alone.

`DailyBundlePreview` itself is retained, because the shadow-rollout QA in the deploy README depends on inspecting its one-, two-, and three-column layouts. Its heading changes to `Last generated test bundle · <localDate>` so it no longer reads as a record of what was emailed.

## Testing

Contract tests follow the existing pattern in `src/features/daily-outfits/__tests__/`, which evaluates `.gs` sources directly through `evaluateAppsScript`.

- Token round-trip signs and verifies; tampered payload, tampered signature, and truncated token are each rejected.
- An out-of-window `localDate` is rejected, with the boundary asserted at exactly 30 days.
- Drain semantics: feedback arriving before its history entry remains in the store, then merges on the next run and is removed.
- Repeated taps on the same `(localDate, candidateId)` resolve last-write-wins.
- Test-mode tokens write nothing.
- Render parity: every generated look emits three links in both HTML and plain text, Encore emits none, and no `appUrl` reference remains.
- End to end: a `wore` tap reaches `dailyHistoryContextV2_` as an `itemFeedbackSignals` entry and exempts those items from `cooldownItemIds`. This assertion is the one that would have caught the current silent breakage.

## Deployment

1. Add `FEEDBACK_SECRET` and `WEB_APP_URL` Script Properties; remove `APP_URL`.
2. Push every `.gs` file and redeploy to the existing deployment id with `clasp deploy -i <id>`, preserving the `/exec` URL. The time-driven trigger runs HEAD, but the web app serves the deployed version, so a push alone will not expose the new `doGet`.
3. Send a test delivery and confirm the links render and report `Test delivery — not recorded`.
4. Confirm a real morning email records a tap and that the signal appears in the next day's planning context.
